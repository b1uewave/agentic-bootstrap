# Staging 與 Production 多環境部署協定

本指南說明了環境隔離的標準規範，並提供了一套問卷，協助您評估您的專案是否需要配置獨立的 Staging（測試/預發布）環境。

---

## 1. Staging 環境決策問卷

請透過以下三個維度評估您的產品發布風險：

### 維度 A：用戶規模與業務影響
> 本應用程式是否會有真實的外部用戶？是否會處理真實的客戶交易或持有關鍵的用戶隱私資料？
- **[ ] 是 (高風險)**：任何 Bug 都會立即導致商譽受損或營業額損失。
- **[ ] 否 (低風險)**：本專案為內部工具、學習用途，或為無商業損失風險的產品。

### 維度 B：外部整合複雜度
> 本專案是否需要串接第三方即時服務（如 Google/Apple 登入、Stripe 金流、Line Pay、或 Webhook 回傳機制）？
- **[ ] 是 (高複雜度)**：需要設定真實的公開回傳網址（Callback URLs）進行線上握手測試。
- **[ ] 否 (低複雜度)**：所有運算皆在本地或單一伺服器內自研完成。

### 維度 C：資料庫變動頻率
> 本專案是否頻繁進行資料寫入、批次遷移（Migrations）或資料表結構（Schema）修改？
- **[ ] 是 (高資料風險)**：結構變更可能導致鎖表（Table Lock）或資料損毀。
- **[ ] 否 (低資料風險)**：無狀態（Stateless）前端網頁，或簡單的唯讀資料層。

---

### 💡 決策建議矩陣

| 評估結果 (獲得「是」的數量) | 建議採取的環境策略 | 分支管理架構 |
| :--- | :--- | :--- |
| **0 個「是」** | **直接部署至正式環境 (Production)** | `main` 作為單一發布分支即可，無需額外維護 staging。 |
| **1 個以上「是」** | **雙環境配置 (Staging + Production)** | 嚴格執行 Git Flow（`develop` 部署至 Staging，驗證無誤後才併入 `main`）。 |

---

## 2. 環境變數與 `.env` 隔離規範

為防止配置洩露並落實環境獨立性：

1. **本地開發**：配置本地 `.env`（已加入 `.gitignore`）。請參考 `.env.example` 來設定必填金鑰。
2. **Staging 環境**：讀取系統變數或託管平台（如 Vercel）設定之變數。
3. **Production 正式環境**：讀取正式環境之系統變數，嚴禁與 Staging 共用同一套資料庫金鑰。
4. **代碼開發鐵律**：所有 API 接口與資料庫連接必須使用動態環境變數。
   ```javascript
   // 🟢 推薦寫法
   const dbUri = process.env.DATABASE_URL;
   
   // 🔴 嚴禁寫法
   const dbUri = "postgresql://localhost:5432/my_production_db"; // 嚴重安全性違規，面試必扣分
   ```

## 3. 自動化測試與上線驗證要求

在將分支從 `develop`（Staging）合併至 `main`（Production）前，AI Agent 必須執行：
- **語法與風格檢查**：執行 `npm run lint` 或 `eslint .` 確保語法無 warnings。
- **單元測試套件**：確保 100% 測試斷言通過。
- **預覽網址驗證**：AI Agent 需點擊並分析 Staging 自動部署產生的 Preview URL，確認 UI 排版與按鈕點擊流程正常。
