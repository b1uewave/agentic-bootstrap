# Staging & Production Deployment Protocol

This guide outlines the environment segregation standards and provides a questionnaire to help you determine if your project warrants a dedicated Staging environment.

---

## 1. Staging Environment Assessment Questionnaire

Run through these four questions to evaluate your release risk profile:

### Question A: Scale & Impact
> Will this application have active external users, processing live client transactions, or holding critical user data?
- **[ ] Yes (High Risk)**: A bug immediately impacts reputation or revenue.
- **[ ] No (Low Risk)**: App is internal, educational, or has a non-critical user base.

### Question B: Integrations
> Does the app require live third-party integrations (OAuth, Stripe Payments, External APIs, Webhooks)?
- **[ ] Yes (High Complexity)**: Requires real-world callback URLs and network handshake testing.
- **[ ] No (Low Complexity)**: All computations are local or self-contained.

### Question C: Database Mutability
> Does the app perform data mutations, batch migrations, or regular schema changes?
- **[ ] Yes (High Data Risk)**: Schema migrations can lock tables or corrupt production data.
- **[ ] No (Low Data Risk)**: No stateful database, or simple read-only data layer.

---

### 💡 Recommendation Matrix

| High Risk Score | Strategy Recommendation | Branching Architecture |
| :--- | :--- | :--- |
| **0 Yes** | **Direct Production Deployment** | `main` acts as the single release branch. |
| **1+ Yes** | **Dual Staging & Production Setup** | Strict Git Flow (`main` for Prod, `develop` for Staging). |

## 2. Environment Variables & `.env` Separation

To prevent configuration leaks and enforce environment isolation:

1. **Local Development**: Configure `.env` (gitignored). Reference `.env.example` for required keys.
2. **Staging Environment**: Read parameters from system environment variables prefixed with `STAGING_` (or configure via your hosting panel like Vercel).
3. **Production Environment**: Read parameters from variables prefixed with `PROD_` (or system environment secrets).
4. **Codebase Rule**: All API calls and DB initializations must dynamically parse variables.
   ```javascript
   // Recommended
   const dbUri = process.env.DATABASE_URL;
   
   // Forbidden
   const dbUri = "postgresql://localhost:5432/my_production_db"; // CRITICAL SECURITY VIOLATION
   ```

---

## 3. Automated Testing Requirements

Before pushing from `develop` (Staging) to `main` (Production), the AI Agent must execute:
- **Linter validation**: `npm run lint` or `eslint .`
- **Unit testing suite**: Ensure 100% assertions pass.
- **Preview validation**: Open and interact with the Vercel/Render preview URL generated by the Staging CI/CD to verify styling and user journeys.
